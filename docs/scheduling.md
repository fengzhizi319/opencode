# 调度与并发策略（针对 `subtask` / `TaskTool` 的补充资料，中文）

本文补充关于子任务调度、并发与资源管理的设计说明、权衡、以及若要修改当前实现（串行 LIFO）的替代方案与注意事项。

当前实现回顾

- `loop()` 在收集到 `subtask` parts 后使用 `tasks.pop()`（LIFO），并在循环体内 `await taskTool.execute(...)` 逐个处理（串行）。
- 这种实现简单、易于调试，并能保证父会话在每个子任务完成后按顺序处理返回结果。

为何选择串行 / LIFO

- 串行保证：
  - 父会话在每个子任务完成并写回结果前，不会被其他子任务的并发写入干扰。
  - 便于维护消息顺序与一致性（尤其是当子任务会在父会话中生成 synthetic messages 或更新同一 resource 时）。
- LIFO（最近优先）的可能原因：
  - 在交互式场景中，最近添加的任务往往更紧急或更相关，优先处理能提高交互体验。
  - 实现上更容易（在反向遍历消息时 push 到数组然后 pop）。

可选策略与改动建议

1) FIFO（先入先出）
- 意图：按 Plan agent 产生顺序处理任务（保持自然语义）。
- 最小改动：把 `tasks.pop()` 改为 `tasks.shift()`（或在收集阶段按正序 push 并 pop）。
- 影响：如果 Plan 生成的是依赖链（后面任务依赖前面结果），FIFO 更直观；若 Plan 生成的是并行可独立任务，FIFO 与 LIFO 差别不大。

2) 并行执行（批量并发）
- 意图：在不需要严格顺序的情况下，提高吞吐与总体完成时间。
- 简单实现（危险点）示例：
  - 在 loop 中收集一批任务（例如最多 N 个），对这 N 个任务并行 `Promise.all(tasks.map(t => TaskTool.execute(...)))`。
- 风险与需要解决的问题：
  - 并发写回：多个子任务同时更新父会话的 parts/消息历史会产生竞态，需要加锁或使用原子化写入策略。
  - 资源控制：并发触发多个子会话会同时发起 LLM 调用，可能引起费用暴增或配额耗尽，需要并发上限与配额守护。
  - 中止处理：abort 时需要同时取消所有正在运行的子会话并正确汇报各自的状态。
  - 权限/安全：确保每个并发子任务的权限上下文正确互相隔离。
- 推荐实现：引入一个并发池（例如并发度 M），使用队列 + worker 线程/协程从队列中拉任务并执行，确保写回逻辑串行化或使用事务。

3) 优先级调度与重试
- 支持优先级：在 `subtask` part 上引入 `priority` 字段（数字或枚举），调度器根据优先级排队执行。
- 重试策略：若子任务执行失败，可按策略重试（带退避、重试次数限制），并把重试记录写入 part 的 metadata。

4) 组合策略（批量 + 串行写回）
- 并发执行子会话以获得速度，但把写回与状态更新集中在一个串行化的步骤中：
  - 并发运行 N 个子会话，将它们的结果先写入临时存储（内存或临时表）。
  - 在单独的写回阶段，按预期顺序把结果合并回父会话（更新 parts，写入 synthetic messages）。
- 优点：并发缩短执行时间，同时保持父会话历史的一致性。

实现细节建议

- 原子写入/事务：父会话的 `Session.updatePart`/`Session.updateMessage` 需要保证并发下不会出现部分写入或覆盖。若后端 DB 支持事务，使用事务来批量提交写回。
- 并发限流：实现固定大小的 worker pool（如 `p-limit` 风格）来控制同一时间发起的子会话数。
- 超时与取消：为每个子任务设置合理的超时并在超时后调用 `SessionPrompt.cancel(childSessionID)`。
- 监控与指标：记录并发子会话数、失败率、平均执行时间、LLM token 消耗等以便容量规划。

测试建议

- 单元测试：模拟 `TaskTool.execute` 成功/失败/抛出异常、父 abort 场景、task 恢复（`task_id`）场景。
- 集成测试：生成多个 subtask，测试 FIFO/LIFO/并发策略在消息历史和父会话写回上的表现。
- 混合负载测试：在受控环境下并发触发大量子任务，校验限流、费用、超时和清理逻辑。

结论

- 当前实现用了简单且稳健的串行 + LIFO 策略，适合以顺序可控和一致性为优先的系统。若需要吞吐提升或不同语义的顺序（如 FIFO），可以基于本文提出的替代方案进行有控制的改造。
