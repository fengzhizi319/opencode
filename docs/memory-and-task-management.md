# Memory System & 任务管理机制

本文档详细介绍了 OpenCode 的 Memory（记忆）系统工作原理，以及面对一个完整的编程任务时，系统是如何分步实现、保证无遗漏、并管理整个项目结构的。

## 1. Memory 系统详解

OpenCode 的 Memory 系统是基于对话历史、文件上下文和项目状态构建的动态上下文管理系统。它的主要职责是确保 LLM 拥有足够的上下文来完成任务，同时避免超出 Token 限制。

### 1.1 短期记忆 (Short-term Memory)
短期记忆即当前 Session（会话）中的近期对话历史。包含：
- 用户的指令与问题。
- LLM 的回复与思考过程（Reasoning）。
- 工具调用的输入与结果（例如读取的文件内容、执行命令的输出）。

### 1.2 上下文压缩与长期记忆 (Context Compaction)
LLM 的上下文窗口是有限的（如 200k tokens）。当上下文接近溢出阈值时，Memory 系统会触发**自动压缩 (Compaction)**：
1. **剪枝 (Pruning)**：从历史记录中移除过时的工具输出（如早期的大型文件读取结果）。
2. **摘要 (Summarization)**：调用专门的 `compaction` Agent 将早期的对话过程总结成精简的摘要状态（Summary State），作为长期记忆保留。
3. **关键信息保护**：注入的 Skill、系统 Prompt 等关键信息会被保护，不会被剪切掉。

## 2. 编程任务的分步实现流程

给 OpenCode 分配一个复杂的编程任务时，系统通常采用**自顶向下、分而治之**的策略。

### 2.1 需求分析与架构设计
任务开始时，最好先要求 Agent 进行架构设计。你可以显式指定使用 `plan` Agent，或者由默认的 `build` Agent 主动决定先进行规划。
- **搜集上下文**：Agent 会先使用 `explore`、`glob`、`read` 等工具熟悉现有代码库。
- **输出设计方案**：Agent 会输出一个架构设计文档或任务拆解清单。

### 2.2 架构设计从何而来？
架构设计通常是结合上下文由 **LLM 动态生成，辅以 Skill 提供的先验知识**：
- **LLM 从头生成**：如果是一个全新的需求，LLM 会凭借强大的基座能力和代码库上下文自己进行设计。
- **Skill 注入约束**：你可以通过编写 `SKILL.md`（作为项目记忆的一部分），强制定义项目的架构规范、目录结构和技术栈。当相关场景触发时，Skill 内容自动加入提示词，指导 LLM 的设计方案。

### 2.3 逐渐代码设计与实现
得到架构后，Agent 会逐步实现每个模块。它可以使用 `run_subagent` 或创建子任务的方式来处理复杂逻辑。
1. 创建或编辑基础组件。
2. 验证和运行测试（使用 bash 工具运行 `bun test` 或 `tsc`）。
3. 修复产生的错误。
4. 提交更改，转入下一个模块。

## 3. 如何保证没有遗漏？

复杂任务容易产生遗漏，OpenCode 通过以下机制来兜底：

1. **TODO 列表与任务树 (Task Tracking)**
   - Agent 通常会在内部推理或使用专用的待办事项工具，来维护一个由粗到细的 TODO 列表。
   - 每完成一个组件，Agent 会回顾原始的 TODO 清单，确认当前进度和下一步操作。
2. **分步反思 (Reflection)**
   - 每执行完一批编辑，Agent 倾向于主动调用编译命令或 Linter 来验证代码的正确性闭环。
3. **Human-in-the-loop**
   - Agent 跑完阶段性计划后，会向用户汇报状态，此时用户可以检查是否有功能的遗漏，并下发下一阶段的补充指令。

## 4. 管理项目的树形结构 (Agent 与子任务)

整个编程项目的执行可以视为一棵**任务树**（包含架构层、模块层、实现层）。Agent 是这样管理这种多层结构的：

1. **Primary Agent (主控制器)**
   - 默认的 `build` Agent 作为主节点（Root节点），负责接收总任务，拆分宏观计划。
2. **Subagents (子智能体分发)**
   - 对于清晰且独立的分支任务，主 Agent 可以选择委托给特定的 Subagent（例如：调用 `explore` 了解陌生目录，或创建专用的通用子 Agent 处理单一文件重构）。
3. **Session 分叉 (Forking)**
   - 对于试错性、分支性的开发（例如尝试重构数据库模型），系统支持对当前 Session 进行 Fork。在子 Session 中尝试不同方案而不会污染主 Session 的历史，最终将成功的修改带回主线。
4. **状态隔离与收敛**
   - 随着深度遍历任务树，底层子任务完成后，相关工具调用的长输出不需要全部返回主线程，只需回传“执行结论”即可，这本身就是对其历史状态（Memory）的有效收敛。
